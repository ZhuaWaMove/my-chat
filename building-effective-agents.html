🎯 核心论点

在过去一年中，我们与数十个在不同行业构建大语言模型（LLM）代理的团队合作。一致地发现，最成功的实现并非使用复杂框架或专用库，而是基于简单、可组合的模式构建。

在这篇文章中，我们分享从客户合作和自身代理构建中学到的经验，为开发者提供构建高效代理的实用建议。

关键洞察： 最成功的代理实现基于简单、可组合的模式，而不是复杂框架。

🔑 关键概念区分

代理（Agents） vs 工作流（Workflows）

工作流： 通过预定义代码路径编排LLM和工具的系统。工作流具有可预测的执行路径，适用于明确定义的任务。

代理： LLM动态指导自身过程和工具使用的系统，保持对任务完成方式的控制。代理更具灵活性和自主性。

在Anthropic，我们将所有这些变体归类为代理系统，但在架构上区分工作流和代理。

注意： 本文中，"代理系统"是总称，包括工作流和代理两种架构模式。

⏰ 何时（以及何时不）使用代理

简单解决方案优先

在构建LLM应用时，我们建议首先寻找最简单的解决方案，仅在需要时增加复杂性。这可能意味着根本不构建代理系统。

权衡考虑

代理系统通常以延迟和成本换取更好的任务性能，您应该考虑这种权衡何时有意义：

  • 工作流的优势： 为明确定义的任务提供可预测性和一致性
  • 代理的优势： 当需要灵活性和模型驱动的决策时
  • 简单方案： 对于许多应用，使用检索和上下文示例优化单个LLM调用通常就足够了

框架使用建议

有许多框架使代理系统更容易实现，包括：

  • Claude Agent SDK
  • AWS的Strands Agents SDK
  • Rivet（拖放GUI LLM工作流构建器）
  • Vellum（另一个用于构建和测试复杂工作流的GUI工具）

建议： 开发者应从直接使用LLM API开始：许多模式可以用几行代码实现。如果使用框架，请确保理解底层代码。

🧱 构建模块：增强的LLM

代理系统的基本构建块是增强的LLM，具有以下能力：

  • 检索（Retrieval）： 获取外部信息
  • 工具使用（Tools）： 调用外部功能
  • 记忆（Memory）： 保留和利用历史信息

我们当前的模型可以主动使用这些能力：生成自己的搜索查询、选择适当的工具、确定保留哪些信息。

实现重点： 我们建议关注两个关键方面：

  1. 为特定用例定制这些能力
  2. 确保它们为LLM提供简单、文档完善的接口

实现这些增强的一种方法是通过最近发布的模型上下文协议（Model Context Protocol），它允许开发者通过简单的客户端实现与不断增长的第三方工具生态系统集成。

🔄 工作流模式

以下是我们在生产中看到的代理系统常见模式：

1. 提示链（Prompt Chaining）

将任务分解为一系列步骤，每个LLM调用处理前一个步骤的输出。可以在任何中间步骤添加程序化检查（如下图中的"gate"）以确保过程正常进行。

适用场景： 任务可以轻松、清晰地分解为固定子任务的情况。

示例： 生成营销文案，然后将其翻译成不同语言；编写文档大纲，检查大纲是否符合某些标准，然后根据大纲编写文档。

2. 路由（Routing）

对输入进行分类并将其引导到专门的后续任务。允许关注点分离，构建更专门的提示。

适用场景： 复杂任务，存在更好单独处理的不同类别，且分类可以由LLM或传统分类模型准确处理。

示例： 将不同类型的客户服务查询（一般问题、退款请求、技术支持）引导到不同的下游流程、提示和工具；将简单/常见问题路由到成本效益更高的模型（如Claude Haiku 4.5），将困难/不寻常问题路由到更强大的模型（如Claude Sonnet 4.5）。

3. 并行化（Parallelization）

LLM有时可以同时处理任务，程序化聚合输出。有两种关键变体：

  • 分段（Sectioning）： 将任务分解为独立并行运行的子任务
  • 投票（Voting）： 多次运行相同任务以获得多样化输出

适用场景： 需要并行化以提高速度，或需要多个视角/尝试以获得更高置信度结果。

示例： 实施防护栏，一个模型实例处理用户查询，另一个筛选不适当内容；自动化评估LLM性能，每个LLM调用评估模型在给定提示上的不同方面。

4. 编排器-工作者（Orchestrator-workers）

中央LLM动态分解任务，将其委托给工作者LLM，并综合它们的结果。

适用场景： 无法预测所需子任务的复杂任务（如编码任务）。

示例： 每次对多个文件进行复杂更改的编码产品；涉及从多个来源收集和分析信息以获取可能相关信息。

5. 评估器-优化器（Evaluator-optimizer）

一个LLM调用生成响应，另一个在循环中提供评估和反馈。

适用场景： 有明确评估标准，且迭代改进提供可衡量价值的情况。

示例： 文学翻译，翻译LLM可能最初无法捕捉细微差别，但评估器LLM可以提供有用批评；需要多轮搜索和分析以收集全面信息的复杂搜索任务。

🤖 代理（自主代理）

随着LLM在关键能力上的成熟，代理正在生产中崭露头角：理解复杂输入、参与推理和规划、可靠使用工具以及从错误中恢复。

代理特征

  • 从人类用户接收命令或进行交互讨论
  • 任务明确后，独立计划和操作
  • 在执行过程中从环境获取"基本事实"（如工具调用结果或代码执行）以评估进度
  • 可以在检查点或遇到阻碍时暂停等待人类反馈
  • 通常任务在完成时终止，但也包括停止条件（如最大迭代次数）以保持控制

何时使用代理

代理可用于开放式问题，其中难以或无法预测所需步骤数，且无法硬编码固定路径。LLM可能运行多个回合，您必须对其决策有一定程度的信任。

注意： 代理的自主性意味着更高的成本和潜在的错误累积。我们建议在沙盒环境中进行广泛测试，并设置适当的防护栏。

代理示例

  • 编码代理： 解决SWE-bench任务，根据任务描述编辑多个文件
  • 计算机使用： Claude使用计算机完成任务

🎯 核心原则

在实现代理时，我们尝试遵循三个核心原则：

1. 保持简单性

保持代理设计的简单性。复杂性只应在明确改进结果时添加。

2. 优先透明度

通过明确显示代理的规划步骤来优先考虑透明度。这有助于调试和建立信任。

3. 精心设计ACI

通过彻底的工具文档和测试精心设计代理-计算机接口（ACI）。工具是代理与外界交互的关键。

框架可以帮助快速入门，但在转向生产时不要犹豫减少抽象层并使用基本组件构建。

📋 附录1：代理实践

我们的客户工作揭示了两个特别有前景的AI代理应用领域，展示了上述模式的实用价值：

A. 客户支持

客户支持结合熟悉的聊天机器人界面和通过工具集成的增强能力。这非常适合更开放的代理，因为：

  • 支持交互自然遵循对话流程，同时需要访问外部信息和操作
  • 可以集成工具来获取客户数据、订单历史和知识库文章
  • 可以程序化处理退款或更新工单等操作
  • 可以通过用户定义的解决方案清晰衡量成功

B. 编码代理

软件开发领域已显示出LLM功能的显著潜力，能力从代码补全发展到自主问题解决。代理特别有效，因为：

  • 代码解决方案可通过自动化测试验证
  • 代理可以使用测试结果作为反馈进行迭代
  • 问题空间定义明确且结构化
  • 输出质量可以客观衡量

📋 附录2：工具的提示工程

无论构建哪种代理系统，工具都可能是代理的重要组成部分。工具使Claude能够通过在我们的API中指定其确切结构和定义来与外部服务和API交互。

工具设计建议

关键原则： 投入与人类-计算机界面（HCI）相同的精力创建良好的代理-计算机界面（ACI）。

我们的工具格式决策建议：

  1. 给模型足够的令牌来"思考"： 避免它陷入困境
  2. 保持格式自然： 接近模型在互联网文本中自然看到的内容
  3. 避免格式化"开销"： 如必须准确计算数千行代码，或对编写的任何代码进行字符串转义

最佳实践

  • 站在模型的角度： 基于描述和参数，使用此工具是否明显？
  • 包含示例： 良好的工具定义通常包括使用示例、边缘情况、输入格式要求和与其他工具的清晰边界
  • 测试工具使用： 在工作台中运行许多示例输入，查看模型犯的错误并进行迭代
  • 防错设计： 更改参数使其更难出错

经验分享： 在构建SWE-bench代理时，我们实际上花了更多时间优化工具而不是整体提示。

📝 总结

LLM领域的成功不在于构建最复杂的系统，而在于为需求构建正确的系统。

实施路径：

  1. 从简单提示开始
  2. 通过全面评估进行优化
  3. 仅当更简单的解决方案不足时才添加多步骤代理系统

遵循这些原则，您可以创建不仅强大而且可靠、可维护且受用户信任的代理。
